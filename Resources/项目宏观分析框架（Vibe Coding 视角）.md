# 项目宏观分析框架 — Vibe Coding 视角

> Vibe Coding ≠ 随便写。它意味着你的代码库不再只是给人看，更是给 AI 看的。
> 分析的出发点也变了：不只是「这个系统怎么工作的」，
> 更是 **「这个系统适合让 AI 迭代吗」**。

---

## 零、Vibe Coding 分析前置

在开始 10 个维度之前，先回答一个元问题：

| 问题 | 意义 |
|------|------|
| **这个项目是手写为主还是 AI 生成为主？** | 决定分析重心：传统项目看可维护性，AI 项目看可迭代性 |
| **AI 能多快上手改一个功能？** | 从提出需求到落地要几步？瓶颈在哪？ |
| **代码库对 LLM 的友好度如何？** | 是不是容易放进 context window？命名/结构是否自解释？ |
| **出错后怎么兜底？** | AI 生成的代码错了，测试能拦住吗？人能看懂吗？ |

---

## 一、业务层 — 它在解决什么问题

| 角度 | 要回答的问题 |
|------|-------------|
| **产品定位** | 一句话说清楚这个系统是什么？它的核心主张是什么？ |
| **用户画像** | 谁在用？解决他们的什么痛点？ |
| **核心流程** | 用户从开始到结束经过哪些步骤？关键路径是什么？ |
| **价值主张** | 它和竞品/替代方案的核心区别在哪？ |
| 🌀 **AI 原生度** | 这个产品的核心流程本身就是 AI 驱动的？还是 AI 只是附属功能？ |

---

## 二、系统架构 — 它是怎么组织的

| 角度 | 要回答的问题 |
|------|-------------|
| **分层架构** | 系统分了哪些层？层间依赖方向？ |
| **模块划分** | 按什么维度拆分模块（按业务域/按技术层/按功能）？ |
| **依赖关系** | 模块间的依赖是单向还是双向？有没有循环依赖？ |
| **扩展性设计** | 新增一个功能需要改几个模块？有没有插件/扩展点机制？ |
| **架构模式** | MVC、六边形、DDD、CQRS、事件驱动还是其他？ |
| 🌀 **AI 可导航性** | **一个不熟悉代码库的 AI 能在几步内找到要改的地方？** 目录结构是否符合直觉？模块边界是否清晰到 LLM 不会搞混？ |
| 🌀 **声明式 vs 命令式** | **配置/声明式越多，AI 越容易改；命令式逻辑越深，AI 越容易出错。** 项目中声明式的比例是多少？ |

---

## 三、数据模型 — 它的世界长什么样

| 角度 | 要回答的问题 |
|------|-------------|
| **核心实体** | 系统里有哪些核心概念（用户/订单/项目）？它们的关系？ |
| **实体关系** | 一对一/一对多/多对多？外键约束？级联策略？ |
| **数据流** | 数据从哪里来、经过哪些处理、流向哪里？ |
| **持久化策略** | 用什么数据库？Schema 怎么设计的？迁移策略？ |
| **状态管理** | 实体有哪些状态？状态转换图？ |
| 🌀 **Schema 即文档** | **AI 主要通过 schema / 类型定义理解数据模型。** Zod / TypeScript 类型 / OpenAPI —— 项目有没有这些「AI 可读」的数据契约？ |

---

## 四、技术栈 — 用什么造的

| 角度 | 要回答的问题 |
|------|-------------|
| **语言与运行时** | 主要语言、运行时环境 |
| **框架与库** | UI 框架、后端框架、ORM、工具库 |
| **构建工具** | 打包、编译、类型检查、代码生成 |
| **测试工具** | 测试框架、模拟库、集成测试方案 |
| **基础设施** | 数据库、缓存、消息队列、部署方式 |
| 🌀 **AI 生态成熟度** | **这个技术栈是否在 LLM 训练数据中充分覆盖？** TypeScript 生态 > 小众语言。流行框架的 AI 补全准确率远高于冷门框架。 |
| 🌀 **开发环境 AI 就绪度** | **项目是否配置了 cursorrules / copilot instructions 等 AI 开发辅助？** 这些直接影响 AI 输出质量。 |

---

## 五、代码组织 — 怎么找到代码

| 角度 | 要回答的问题 |
|------|-------------|
| **目录结构** | 文件按什么规则组织（按类型/按模块/按功能）？ |
| **命名规范** | 包名、文件名、类名、函数名有统一风格吗？ |
| **模块边界** | 每个模块的公开 API 是什么？内部实现如何隐藏？ |
| **入口与出口** | 程序的入口在哪？路由/控制器如何注册？ |
| 🌀 **LLM Context 效率** | **一个典型功能的完整实现链（路由→逻辑→数据）需要读多少个文件？** 文件太碎 → context 装不下；文件太大 → 找不到关键逻辑。 |
| 🌀 **自解释程度** | **不写注释 AI 也能猜出这段代码在做什么？** 命名是否足够语义化？类型是否表达了意图？ |
| 🌀 **LSP 友好度** | TypeScript / Zod / JSDoc 等支持跳转定义的类型信息越多，AI 选型越准确。 |

---

## 六、接口与契约 — 怎么交互

| 角度 | 要回答的问题 |
|------|-------------|
| **API 设计** | RESTful/GraphQL/RPC？路由如何组织？ |
| **请求链路** | 一个请求从客户端到数据库经过哪些中间件/处理器？ |
| **数据格式** | 请求/响应的 schema 定义？有没有类型校验？ |
| **错误处理** | 错误码体系？统一错误格式？ |
| **认证与授权** | 用户身份如何验证？权限如何控制？ |
| 🌀 **API 的 AI 可发现性** | **有没有 OpenAPI / GraphQL schema 这类 AI 可以直接读的 API 定义？** 这决定了 AI 能否自动帮你写 API 调用代码。 |
| 🌀 **契约优先** | 接口定义是否先于实现？类型是否在路由 handler 中复用？ |

---

## 七、状态与生命周期 — 事情怎么跑

| 角度 | 要回答的问题 |
|------|-------------|
| **启动流程** | 系统启动时做了什么初始化？ |
| **运行时编排** | 核心业务逻辑的执行流程是顺序/状态机/事件驱动/管线？ |
| **会话与上下文** | 用户会话如何管理？跨请求的上下文怎么传递？ |
| **生命周期** | 对象/组件/会话从创建到销毁的完整过程？ |
| **并发模型** | 异步/同步/多线程/事件循环？ |
| 🌀 **管线可视化** | **编排逻辑是显式的（如声明式路由图/管线步骤）还是隐式的（散落在各处回调中）？** 显式编排 = AI 可读、可改、可追踪。 |
| 🌀 **副作用隔离** | 纯函数和副作用是否清晰分开？AI 改错副作用代码的破坏性远大于改错纯函数。 |

---

## 八、质量与可观测性 — 怎么保证不出事

| 角度 | 要回答的问题 |
|------|-------------|
| **测试策略** | 单元测试/集成测试/E2E 的分工？ |
| **错误边界** | 关键路径上的容错/降级/重试策略？ |
| **日志与追踪** | 怎么记录运行时信息？如何追踪请求链路？ |
| **监控指标** | 系统健康度的关键指标是什么？ |
| **防御性编程** | 输入校验、类型守卫、断言？ |
| 🌀 **测试即护栏** | **Vibe Coding 最核心的安全机制。** AI 生成代码后，测试是第一个也是最重要的验证层。测试覆盖率够吗？测试本身是 AI 能理解和维护的吗？ |
| 🌀 **Mock 模式** | 项目是否支持 mock 运行（无需真实 LLM/外部依赖即可测试）？这决定了 AI 迭代速度——每次改完能不能秒级验证。 |
| 🌀 **类型即文档** | TypeScript 类型 / Zod schema / 接口定义 本身就是 AI 理解代码的最可靠来源。项目在这方面的投入度？ |

---

## 九、开发状态 — 做到哪了

| 角度 | 要回答的问题 |
|------|-------------|
| **完成度评估** | 各模块/功能的完成百分比？ |
| **已落地 vs 待做** | 哪些是已经实现的？哪些是规划但未做的？ |
| **技术债务** | 代码中的临时方案、未重构的部分、已知问题？ |
| **风险点** | 架构中最脆弱的部分在哪？什么情况下会出问题？ |
| 🌀 **AI 友好度评分** | **这个项目当前状态 AI 上手改的难度是低/中/高？** 主要卡点在哪（context 太大/类型缺失/测试空白/副作用混乱）？ |

---

## 十、部署与运维 — 怎么跑起来

| 角度 | 要回答的问题 |
|------|-------------|
| **环境配置** | 开发/测试/生产环境的配置管理方式？ |
| **构建与部署** | CI/CD 流程？构建产物？ |
| **依赖管理** | 外部依赖的版本管理策略？ |
| **DevOps** | Docker/K8s/脚本部署？启动脚本？ |
| 🌀 **一键可运行** | **AI 改完代码能不能一键验证？** 启动脚本是否清晰？依赖安装是否自动化？这是 vibe coding 迭代速度的关键瓶颈。 |

## 分析顺序建议

```
① 业务层（理解领域）   ─→  ⑥ 接口层（看边界）
                              ↓
② 架构 + ⑤ 代码组织（看骨架）
      ↓
③ 数据模型（看核心）   ─→  ④ 技术栈（看工具）
                              ↓
⑦ 状态与生命周期（看运行）
      ↓
⑧ 质量（看可靠性）     ─→  ⑨ 开发状态（看进展）
                              ↓
⑩ 运维（看落地）
```

### Vibe Coding 视角下的关键信号

| 信号 | 绿灯 🟢 | 红灯 🔴 |
|------|---------|---------|
| **AI 可导航性** | 目录结构直观，模块边界清晰 | 文件散乱，单文件 > 1000 行 |
| **类型完备度** | TypeScript + Zod schema 全覆盖 | `any` 遍地，缺少类型定义 |
| **测试护栏** | 各层有测试，可 mock 运行 | 测试缺失或依赖外部服务 |
| **声明式比例** | 配置驱动，管线显式编排 | 逻辑深埋在回调/if-else 中 |
| **启动速度** | `npm install && npm run dev` 搞定 | 需要 5 步以上手动配置 |
| **LLM 上下文效率** | 改一个功能读 2-3 个文件 | 需要读 8+ 个文件才能理解完整链路 |
