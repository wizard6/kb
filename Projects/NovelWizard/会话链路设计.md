# NovelWizard 会话链路设计文档

> 说明我的理解：你觉得对项目把握程度低，不是因为你没读够代码，而是因为你缺少一张「全链路地图」—— 每个节点是什么、为什么存在、怎么连起来的、改哪里会影响到哪里。
>
> 这份文档就是那张地图。

---

## 一、设计目标

会话链路回答一个核心问题：**用户说了一句话之后，系统应该做什么？**

| 目标 | 说明 |
|------|------|
| **灵活路由** | 不是所有输入都需要调 AI —— 斜杠命令走 Skill、委托走 Agent、普通对话走 chat |
| **可观测** | 每一跳的决策过程可追溯、可断点、可调试 |
| **可扩展** | 新增一种「行为」只需注册 Handler，不修改路由逻辑 |
| **可管控** | 每个步骤可独立开关（观测台控制），不会因为某一步挂了就整条链路崩溃 |

---

## 二、整体架构（三层模型）

```
┌─────────────────────────────────────────────────────────────┐
│  层1: 路由决策层（TurnFlow）                                  │
│  决定：本轮走哪条路                                           │
│  文件：packages/skills/src/turnFlow/                          │
│  性质：纯逻辑，无副作用                                        │
├─────────────────────────────────────────────────────────────┤
│  层2: 执行调度层（Dispatch）                                   │
│  决定：按路由结果执行哪个管线                                   │
│  文件：packages/chat-runtime/src/pipeline/dispatch*.ts        │
│  性质：调度器，分派到具体执行器                                  │
├─────────────────────────────────────────────────────────────┤
│  层3: 执行管线层（Pipeline）                                   │
│  决定：每一步做什么、调用什么、返回什么                          │
│  文件：packages/chat-runtime/src/pipeline/send*.ts            │
│  性质：实际的 AI 调用 + 数据处理                                │
└─────────────────────────────────────────────────────────────┘
```

**为什么分三层？**

因为「去哪儿」和「去了之后做什么」是两个不同的问题。分开之后：
- 想改路由规则 → 只改第 1 层
- 想加一种新的执行管线 → 只改第 2 层
- 想调 AI 调用参数 → 只改第 3 层

## 三、第 1 层：路由决策

### 3.1 路由图

```
用户输入
  │
  ├→ order 0:  fixed:delegate
  │   规则：当前 turn 的 meta 中是否有 delegateTarget
  │   命中：交给另一个 Agent 处理，当前 Agent 等待结果
  │   产出：TurnFlowResolution { action: 'delegate', agentId, message }
  │
  ├→ order 10: fixed:flow-continue
  │   规则：上一轮 assistant 回复中是否包含 flowNext 指令
  │   命中：继续执行 flowNext 中指定的 Skill/Agent
  │   产出：TurnFlowResolution { action: 'skill'|'delegate'|'loop' }
  │
  ├→ order 20: fixed:skill-select
  │   规则：输入匹配斜杠命令 / 关键词
  │   命中：执行匹配的 Skill
  │   产出：TurnFlowResolution { action: 'skill', skillId }
  │   [gate: skill-select] 可关闭
  │
  ├→ order 30: model:route
  │   规则：让 LLM 判断用户意图
  │   命中：LLM 返回应该走哪个 Skill
  │   产出：TurnFlowResolution { action: 'skill', skillId, reason }
  │   [gate: skill-select + flow-model-route] 两个都开才走
  │
  └→ order 40: fallback:chat
       规则：以上都没命中
       命中：走普通对话
       产出：TurnFlowResolution { action: 'chat' }
```

### 3.2 设计要点

| 决策 | 为什么 |
|------|--------|
| **order 排序** | 确定性高的放前面（delegate > 关键词 > LLM），避免不可预测的 LLM 调用开销 |
| **gate 机制** | 观测台可以关闭某个路由节点，这在调试时极有用——比如关掉 LLM 路由，看系统是不是只靠关键词也能正常工作 |
| **fixed  vs model** | 规则锁定的归规则锁定，模型判断的归模型判断。不会出现「模型决定要不要走规则」这种递归陷阱 |
| **fallback 兜底** | 所有路由都失败时不会崩溃，走回最安全的 chat |

## 四、第 2 层：执行调度

路由决策产出 `TurnFlowResolution` 后，`dispatchWorkshopTurn` 根据 `action` 分派：

```
TurnFlowResolution { action }
  │
  ├→ 'delegate'
  │   调用 runtime.delegate()
  │   委托给另一个 Agent（如 workshop-discussion → planner-agent）
  │   委托时传递完整对话历史 + 种子上下文
  │   被委托 Agent 独立执行一轮，返回结果
  │
  ├→ 'skill'
  │   调用 sendSkillMessage()
  │   通过 skill-run API 或 function-bus 执行 Skill
  │   支持 mock/LLM 双路径
  │   产出：Skill 执行结果 + 自然语言摘要
  │
  └→ 'chat'
      调用 sendWorkshopMessage()
      走完整对话管线（见下）
```

## 五、第 3 层：对话管线（核心）

这是最复杂的部分，`sendWorkshopMessage` 内有完整的步骤链：

### 5.1 步骤序列

```
输入: input { draft, turns, seed, ... }
  │
  ├── ① sanitizeUserText
  │    清洗输入文本（去空格、截断、规范化）
  │    产出: { cleaned, original }
  │
  ├── ② [gate: knowledge-retrieve]  decomposeUserIntents + retrieveKnowledge
  │    分析用户意图 + 从知识库检索相关内容
  │    可关闭：在观测台关掉 knowledge-retrieve gate 后跳过
  │    产出: { query, entryCount, retrievedBlock, source }
  │    数据流向：retrievedBlock → buildInspirationChatMessages
  │
  ├── ③ resolveSkillDocumentForTurn
  │    根据用户输入匹配应该挂载哪个 Skill 的文档
  │    产出: { catalogMetaBlock, mountedBlock, match? }
  │    数据流向：mountedBlock → buildInspirationChatMessages
  │
  ├── ④ buildInspirationChatMessages
  │    组装 AI 对话消息数组
  │    输入：seed, docRawInput, chatTurns, userMessage, persona,
  │          retrievedKnowledgeBlock, skillCatalogMetaBlock, mountedSkillBlock
  │    产出: ChatMessage[]（即发送给 LLM 的完整 prompt）
  │
  ├── ⑤ postChat
  │    调用 LLM（通过 @novel-wizard/ai-provider）
  │    支持：多模型切换、SSE 流式、mock 模式
  │    产出: { assistantText }
  │
  ├── ⑥ extractFlowDirectiveFromContent
  │    从 AI 回复中提取 flowNext 指令
  │    这是「AI 声明下一步」的关键机制
  │    产出: { directive, visibleContent }
  │    数据流向：directive → 下一轮 order 10 的输入
  │
  └── ⑦ [gate: validate] 后处理
       产出校验（可选）
       可关闭
```

### 5.2 上下文组装细节

`buildInspirationChatMessages` 的输入分层决定了 AI「看到」什么：

```
┌── System Prompt（系统角色）─────────────────────┐
│  persona system prompt（Agent 角色设定）         │
├── Context 层 ──────────────────────────────────┤
│  种子上下文（seed → setting / conflict / ...）  │
│  知识检索块（retrievedKnowledgeBlock）           │
│  Skill 文档（catalogMetaBlock + mountedBlock）  │
├── History 层 ──────────────────────────────────┤
│  活跃对话历史（activeChatTurns）                  │
├── Current 层 ──────────────────────────────────┤
│  本轮用户输入                                    │
└─────────────────────────────────────────────────┘
```

### 5.3 回合数据结构

每一轮对话产生两个 `ChatTurn`（用户 + AI），以及持续的 `session_state`：

```
ChatTurn {
  id: string;
  role: 'user' | 'assistant';
  content: string;
  meta?: {
    agentId?: string;           // 哪个 Agent 处理的
    skillId?: string;           // 触发了哪个 Skill
    flowPhase?: 'fixed' | 'model';  // 哪层路由命中的
    flowRuleId?: string;        // 哪个规则命中的
    flowNext?: TurnFlowDirective;  // AI 声明的下一跳
    knowledgeQuery?: string;    // 检索了什么
    knowledgeEntryCount?: number;
    knowledgeRetrievedBlock?: string;
    knowledgeSource?: string;
    delegateTarget?: string;    // 委托给谁了
  };
}

session_state 持久化到 SQLite（session_state 表）:
{
  scopeKey, sessionId, versionId,
  chatTurns: ChatTurn[],        // 完整对话历史
  skillResults: {},             // Skill 执行结果缓存
  completeness: null,           // 种子完整度
  docRawInput: string,          // 文档草稿
  docSyncedSections: string[]   // 已同步的板块
}
```

## 六、完整数据流示例

以用户输入 `/parse 我有一个关于末日废土的故事……` 为例：

```
Step 1: 路由决策
  └→ sanitizeUserText → resolveTurnFlow
      → skill-select: 匹配 "/parse"
      → TurnFlowResolution { action: 'skill', skillId: 'inspiration-parse' }

Step 2: 执行调度
  └→ dispatchWorkshopTurn: action === 'skill'
      → sendSkillMessage({ skillId: 'inspiration-parse', raw: '...' })

Step 3: Skill 执行
  └→ POST /api/skills/run { skillId, raw }
      → inspirationParsePipeline
        → LLM 解析 → 结构化种子
        → 存入 seeds 表
      → 返回 { result, summary }

Step 4: 轮次记录
  └→ 生成 userTurn（含 meta: { skillId, strategyId }）
     → 生成 assistantTurn（含 meta: { skillId, summary }）
     → append 到 turns[]
```

## 七、扩展点

如果你想修改或扩展这个链路，以下是最小干预的入口：

| 你想做什么 | 改哪里 | 不改哪里 |
|-----------|--------|----------|
| 加一个新的路由规则 | `graph.ts` 加一个 node + `hardcoded.ts` 加对应的 rule handler | 不动 pipeline |
| 加一个新的 Skill | `skills/catalog.ts` 注册 + 加 handler 文件 | 不动路由和管线 |
| 改 AI 上下文中注入的内容 | `buildInspirationChatMessages`（chat-domain 包） | 不动管线流程 |
| 改对话历史裁剪策略 | `activeChatTurns`（chat-domain 包） | 不动管线流程 |
| 关掉知识检索功能 | 观测台关 `knowledge-retrieve` gate | 不动代码 |
| 加一种新的路由 action | `TurnFlowActionKind` 加类型 + dispatch 加分支 | 不动现有路由 |

## 八、与常见模式的对比

| 对比项 | NovelWizard 的做法 | 常见做法 | 区别 |
|--------|-------------------|----------|------|
| 路由决策 | 声明式路由图（data-driven） | if-else 链 | 路由图可读、可改、可观测 |
| AI 调用 | 统一 postChat 接口 + Provider 抽象 | 直接调 SDK | 可切换模型、可 mock |
| 上下文管理 | 分层打包（seed/knowledge/skill/history） | 全部塞进 prompt | 可控、可调试 |
| Skill 执行 | catalog + handler 注册表 | 硬编码函数调用 | 可扩展、可独立分发 |
| 可观测性 | step gate + trace + gui-dev | logger.info | 可控制、可交互 |
| 持久化 | session_state 存完整对话 + Skill 结果 | 只存对话 | 可恢复完整工作状态 |
