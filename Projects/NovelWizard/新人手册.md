## 一、这项目是做什么的？

**一句话**：一个「从灵感种子生长出故事世界」的 AI 小说创作系统。

**不是**一键成书生成器。用户输入零散的灵感（一个世界观设定、几个人物、一段冲突），AI 帮你解析为结构化种子，然后通过多轮对话和 Skill 操作逐步完善，最终产出完整的小说正文。

**更长远的定位**：它还是一个通用的 AI Agent 基座框架。换掉领域模型、注册新 Skill、换掉 UI Shell，就能变成另一个 AI 原生应用。

```
┌─ apps ──────────────────────────────────────┐
│  gui (:4990)      ← 产品 UI（当前最空）      │
│  gui-console (:4993) ← 故事操作系统壳        │
│  gui-dev (:4992)   ← 开发者观测台            │
│  gui-api (:4991)   ← Express API 服务        │
├─ packages ───────────────────────────────────┤
│  domain       ← 类型 + Zod + normalize       │
│  db           ← SQLite schema + migration    │
│  repositories ← 数据访问（Repository 模式）   │
│  ai-provider  ← 多模型抽象 + chat + SSE      │
│  skills       ← Skill catalog + 路由选择     │
│  chat-domain  ← 对话模型 + 消息组装          │
│  chat-runtime ← Agent 运行时 + 管线编排      │
│  chat-shell-ui ← 对话壳层 UI 组件            │
│  context-builder ← 上下文分层打包             │
│  llm-utils    ← 反幻觉 + 安全 JSON 解析      │
│  zero-memory  ← 统一数据获取协议              │
│  silicon-reflection ← 规划器-执行器协议       │
│  app-store    ← Vue 状态管理                 │
│  gui-env      ← Vue composable + 环境工具    │
│  gui-theme    ← 设计 token                   │
│  knowledge-index ← 标签索引                   │
│  scoped-state ← 作用域状态管理                │
└──────────────────────────────────────────────┘
```

### 核心数据流

```
用户输入
  → gui / gui-console（UI 层）
    → app-store（状态管理）
      → POST /api/*（Express 薄路由）
        → skills 或 repositories（业务逻辑）
          → ai-provider（AI 调用）/ db（SQLite）
```

### AI 编排流（核心复杂度）

```
用户输入
  → skill-select（斜杠命令/关键词/LLM 路由）
  → knowledge-retrieve（检索知识库，可选）
  → document-load（加载 Skill 文档，可选）
  → chat（调用 LLM）
  → validate（校验输出，可选）
```

每一步可独立开关（step gate），所有输入输出可追踪（trace）。

## 五、必须遵守的工程纪律

### 5.1 模块化优先，效率兜底

每加一个功能前问自己：
- 这是独立模块吗？有明确的输入/输出吗？
- 注册新模块需要修改已有代码吗？（答案应该是「不需要」）
- 如果是新功能，它有没有自己的 handler 文件？

### 5.2 先类型，后实现

```typescript
// 正确顺序：
interface Foo { ... }    // 1. 定义类型
const fooSchema = z.object({ ... })  // 2. schema 校验
function normalizeFoo(raw): Foo { ... }  // 3. normalizer
// 4. 实现业务逻辑
```

### 5.3 测试是护栏

- 改 AI 编排逻辑之前，确保 `chat-runtime` 的测试通过
- 新加 Skill 必须带测试（至少 mock 执行 + 验证输出格式）
- 路由层改动必须跑 Supertest 集成测试

### 5.4 不要继承债务

- 遇到 `.mjs` 文件就顺手改成 `.ts`
- 遇到绕过 Repository 的查询就改成走 repos
- 大 JSON 字段往分表方向思考

## 六、常见陷阱

| 陷阱 | 说明 |
|------|------|
| **过度架构** | 项目已有 17 个包，不要在没跑通核心前再拆新的 |
| **忽视测试** | 这是最大的坑。没有测试保护，AI 编排代码没人敢改 |
| **先做 UI** | UI 是最后一步。优先保证 API + 编排 + Skill 全链路可跑通 |
| **完美主义** | 架构可以迭代，不要求第一次就完美。先跑通，再优化 |
| **SQLite 陷阱** | 原型阶段 SQLite 够用，但别在上面堆复杂的查询逻辑 |
| **AI 输出全信** | 每次 LLM 返回都要做 `parseJsonSafe` 防御，都有 try-catch |

## 八、你的心态

这个项目的架构底子是好的——分层、类型、模块化、可观测性，这些核心决策没有错。问题在于**一致性**：部分代码跟上了设计，部分没跟上。

你的工作不是重写，是**对齐**：把没跟上的部分拉到跟设计一致的水平。

> 「做得对」比「做得快」重要。但「跑得通」比「做得完美」更重要。
