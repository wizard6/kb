# NovelWizard 技术选型分析

> 分析 NovelWizard Ver.0.1.0 的各项技术选型决策，包括选了什么、为什么、替代方案和推荐建议。
> 
> 评价标准：适合 AI 应用开发的优先级（可迭代性 > 性能 > 生态成熟度 > 学习曲线）。

---

## 1. Monorepo 管理

| 项目 | 选择 |
|------|------|
| NovelWizard | **npm workspaces** |
| 配置文件 | 根 package.json 的 `workspaces: ["packages/*", "apps/*", ...]` |
| 包数量 | 17 packages + 4 apps |

### 评价

| 维度 | 评分 | 说明 |
|------|------|------|
| 上手难度 | 🟢 低 | npm 内置，零配置 |
| 依赖管理 | 🟡 中 | hoisting 行为有坑，依赖版本冲突需手动 |
| 构建缓存 | 🔴 弱 | 无内置缓存，每次全量 build |
| AI 友好度 | 🟢 高 | 结构直观，AI 容易理解 package 边界 |

### 替代方案

| 方案 | 优势 | 劣势 | 适合场景 |
|------|------|------|----------|
| **npm workspaces** ✅ | 零依赖，内置 | 缓存弱，无原生发布支持 | 小中规模 monorepo（< 20 包） |
| **pnpm workspaces** | 磁盘效率高，严格隔离 | 需安装 pnpm | 大型 monorepo，依赖多 |
| **Turborepo** | 缓存 + 并行构建 + remote cache | 增加工具链复杂度 | 需要构建优化的中大型项目 |
| **Nx** | 完整 monorepo 工具链 | 学习曲线高，配置重 | 企业级超大型 monorepo |

### 结论

**npm workspaces 对 NovelWizard 当前阶段是合理选择**。17 个包的数量还没到必须上 Turborepo 的程度。但如果构建时间成为瓶颈（当前 `verify:workspace` 跑一次较慢），迁移到 Turborepo 或 pnpm 是自然演进方向。

## 2. 前端框架

| 项目 | 选择 |
|------|------|
| NovelWizard | **Vue 3 (Composition API) + Vite** |
| 版本 | Vue ^3.4.0, Vite ^5.x |

### 评价

| 维度 | 评分 | 说明 |
|------|------|------|
| 响应式 | 🟢 好 | Vue 3 的 Proxy 响应式比 React 的 re-render 更精确 |
| TypeScript | 🟢 好 | Vue 3 的 `<script setup>` + TS 体验成熟 |
| AI 上下文效率 | 🟢 好 | SFC 结构稳定，AI 容易理解组件边界 |
| 生态成熟度 | 🟢 好 | 中文文档完善，社区活跃 |
| AI 生成质量 | 🟢 好 | Vue 3 在 LLM 训练数据中覆盖充分 |

### 替代方案

| 方案 | 优势 | 劣势 | 适合场景 |
|------|------|------|----------|
| **Vue 3** ✅ | 响应式精确，SFC 结构清晰，中文生态 | 灵活性不如 React | 中后台 + 内容型应用 |
| **React** | 生态最大，hooks 灵活，React Server Components | re-render 优化成本高 | 复杂交互 + 大型社区需求 |
| **Svelte** | 编译时，产物最小，上手简单 | 生态小，AI 训练覆盖不足 | 小型应用，性能敏感 |
| **SolidJS** | 性能极致，细粒度响应式 | 生态小，AI 训练数据少 | 高性能场景 |

### 结论

**Vue 3 是正确的选择**。对于 NovelWizard 这种内容型、中后台为主的应用，Vue 3 的响应式系统天然适合文档编辑场景。Vite 作为构建工具也是当前最佳实践。

## 4. 后端框架

| 项目 | 选择 |
|------|------|
| NovelWizard | **Express** |
| 实现 | `.mjs` 文件，中间件模式 |

### 评价

| 维度 | 评分 | 说明 |
|------|------|------|
| 生态 | 🟢 最大 | Express 生态无可争议 |
| AI 熟悉度 | 🟢 极高 | Express 模式在 LLM 训练数据中覆盖最深 |
| 性能 | 🟡 中 | 相比 Fastify/Hono 有明显差距 |
| 类型安全 | 🔴 弱 | 无原生 TypeScript 集成，路由参数无类型推断 |
| 现代性 | 🔴 弱 | 中间件模型老旧，异步错误处理需手动包装 |

### 替代方案

| 方案 | 优势 | 劣势 | 适合场景 |
|------|------|------|----------|
| **Express** | 最大生态，AI 最熟悉，最稳定 | 性能一般，类型弱 | **原型 + 中小型项目** |
| **Fastify** | 性能 2-3x Express，内置 Schema 校验 | 插件生态略小 | 性能敏感的 API 服务 |
| **Hono** | 极致轻量，多运行时（Node/Deno/CF Workers） | 生态最小 | 边缘计算 + 新项目 |
| **NestJS** | 完整架构（DI/Guard/Interceptor），类型安全 | 学习曲线陡，样板代码多 | 企业级大型后端 |

### 结论

**Express 对现阶段合适，但建议关注 Hono 作为迁移方向**。NovelWizard 已实现了「薄路由 + Repository 层」的架构，这个抽象层使得后端框架切换的成本可控。如果项目增长，从 Express 迁移到 Hono 或 Fastify 的工作量主要在路由定义层。

## 5. 数据库

| 项目 | 选择 |
|------|------|
| NovelWizard | **SQLite（sql.js）** |
| 运行模式 | WAL（Write-Ahead Logging） |
| 访问方式 | 运行时嵌入，Node.js 中直接调用 |

### 评价

| 维度 | 评分 | 说明 |
|------|------|------|
| 启动速度 | 🟢 极快 | 零外部依赖，进程内运行 |
| 部署复杂度 | 🟢 极低 | 文件级管理，无需数据库服务 |
| AI 开发友好 | 🟢 高 | 重置/迁移/测试方便 |
| 并发能力 | 🔴 弱 | SQLite 写锁，不适合高并发 |
| 多用户场景 | 🔴 不支持 | 无网络协议，无法远程访问 |
| 扩展性 | 🔴 差 | 单文件，无法水平扩展 |

### 替代方案

| 方案 | 优势 | 劣势 | 适合场景 |
|------|------|------|----------|
| **SQLite (sql.js)** ✅ | 零运维，原型阶段最优 | 并发差，无网络 | 原型 + 单机应用 |
| **SQLite (better-sqlite3)** | 性能更好，同步 API | 需 native 编译 | Node.js 原生场景 |
| **PostgreSQL** | 完整 RDBMS，JSON 支持好，并发强 | 需维护数据库服务 | 多用户生产环境 |
| **Turso (libsql)** | SQLite 兼容 + 分布式 | 相对新，生态未成熟 | 需要 SQLite 的可移植性 + 远程访问 |

### 结论

**SQLite（sql.js）是原型阶段的正确选择，但需要明确的迁移路径**。NovelWizard 通过 Repository 层 (`@novel-wizard/repositories`) 抽象了数据访问，这个抽象是关键的保险——切换到 PostgreSQL 时，只需要替换 repository 实现，业务代码不受影响。

⚠️ **风险**：当前 mix 了 `.mjs` 的 raw SQL 查询和 repository 模式，部分查询直接写在 route handler 中，这会增加迁移成本。

## 5.5 向量数据库

| 项目 | 选择 |
|------|------|
| NovelWizard | **无** — 当前用 SQLite TEXT 字段存 JSON 数组 `[0.1, 0.2, ...]`，应用层做余弦相似度 |
| 现状 | `embeddings` 表存在，`vector` 字段为 TEXT，无索引，无专门向量引擎 |

### 问题

当前方案在小规模（< 1000 条）下勉强可用，但存在三个硬伤：

| 问题 | 影响 | 临界点 |
|------|------|--------|
| **全表扫描** | 每次搜索需加载所有向量到内存逐一计算 | > 1000 条后延迟明显 |
| **无索引** | 无法做 ANN（近似最近邻）加速 | 数据量再大也不可用 |
| **JSON 解析开销** | TEXT 存 JSON 每次要 parse，CPU 浪费 | 持续存在 |

### 方案对比

#### 方案 A：SQLite 扩展

| 选项 | 原理 | 优势 | 劣势 |
|------|------|------|------|
| **sqlite-vec** | SQLite 的向量搜索扩展，纯 C 实现 | 零额外服务，与现有 SQLite 共用事务 | 相对新（2024），生态未成熟 |
| **sqlite-vss** | 基于 Faiss 的 SQLite 扩展 | 索引能力更强 | 维护已停滞，不推荐新项目 |

#### 方案 B：嵌入式向量数据库

| 选项 | 原理 | 优势 | 劣势 |
|------|------|------|------|
| **zvec 🆕** | 阿里开源的进程内向量数据库，C++ 核心 + Node.js SDK | 功能齐全（密集/稀疏向量、FTS、混合搜索、DiskANN），阿里内部生产验证，Node.js SDK 官方维护 | 独立存储，与 SQLite 数据隔离需同步 |
| **ChromaDB** | 嵌入式向量数据库，有 Node.js SDK | API 简洁，客户端模式无需服务 | Python 核心，Node.js 绑定不稳定；多一套存储 |
| **LanceDB** | 列式向量数据库，Rust 实现 | 快，支持多模态 | 与现有 SQLite 数据隔离，需维护同步 |
| **Qdrant (本地模式)** | 磁盘存储，支持 WASM | 性能好，成熟 | 引入新存储层，增加部署复杂度 |

#### 方案 C：关系型数据库自带向量

| 选项 | 优势 | 劣势 |
|------|------|------|
| **PostgreSQL + pgvector** | 最成熟的方案，支持索引和过滤 | 需要从 SQLite 迁移到 PG，对原型阶段过重 |
| **SQLite + 自定义余弦**（当前） | 最简单 | 不可扩展，仅适合 demo |

### zvec 深度分析

zvec 是**此次新增的推荐选项**，必须认真对待。

| 维度 | zvec | sqlite-vec |
|------|------|------------|
| 定位 | 独立嵌入式向量数据库 | SQLite 扩展 |
| 安装 | `npm install @zvec/zvec` | SQLite 加载扩展 |
| 存储 | 独立目录（`./zvec_data/`） | 共用 SQLite `.db` 文件 |
| FTS 全文检索 | ✅ 原生支持 | ❌ 需要额外 SQLite FTS 扩展 |
| 混合搜索 | ✅ 向量 + 全文 + 标量过滤 | ⚠️ 需手动组合 |
| 稀疏向量 | ✅ 支持 | ❌ |
| DiskANN 索引 | ✅ 支持 | ❌ |
| 阿里内部验证 | ✅ 生产环境验证 | ❌ 社区项目 |
| Node.js SDK | ✅ 官方维护 | ✅ 可用 |
| 数据一致性 | 独立 WAL，与 SQLite 无事务关联 | 与 SQLite 共用事务 |

**zvec 的强项**：
- 功能完整度远超 sqlite-vec：FTS + 混合搜索对 NovelWizard 的「知识库语义搜索 + 关键词搜索」场景极有价值
- 阿里内部打过的生产负载，稳定性有背书
- Node.js SDK 是一等公民，不是社区绑定
- v0.5.0 (2026-06)，迭代活跃

**zvec 的代价**：
- 多一套存储管理（zvec 数据目录 + SQLite 数据库）
- 数据同步：结构化数据在 SQLite，向量在 zvec，需要应用层维护一致性
- 增加一个 native 依赖（C++ 核心，通过 npm 安装时自动下载预编译包）

### 推荐路线（更新版）

```
Phase 1（原型）         Phase 2（生产）                  Phase 3（规模）
─────────────────────────────────────────────────────────────────────────
SQLite TEXT 存 JSON    → zvec 独立嵌入                  → PostgreSQL + pgvector
应用层余弦相似度        → Node.js SDK 调用                → 分布式向量索引
< 500 条               → 500-10K 条（FTS + 混合搜索）    → 10K+
```

### 对 NovelWizard 的建议（更新版）

| 建议 | 理由 |
|------|------|
| **短期** 保持当前 TEXT 方案 | embeddings 功能尚未完全实现，数据量很小，不值得先投 |
| **中期** 优先考虑 **zvec** 而非 sqlite-vec | 功能完整度、阿里生产验证、Node.js 官方 SDK 三个原因。代价是多一套存储管理，但对 NovelWizard 的体量来说可接受。|
| **长期** 评估 PG + pgvector | 如果项目发展到多用户 + 服务端部署 |

### 关键结论

**zvec 是目前最值得关注的选项**。相比 sqlite-vec，它功能更全（FTS + 混合搜索正是写作类应用需要的）、验证更充分（阿里内部）、Node.js 集成更完整（官方 SDK）。代价是多一套存储，但在 NovelWizard 的本地优先架构下，这个代价可控。

> 一句话：**sqlite-vec** 胜在「最简单」，**zvec** 胜在「最完整」。对 NovelWizard 来说 zvec 更值得中期投入。

## 6. AI 模型与提供方

| 项目 | 选择 |
|------|------|
| NovelWizard | **DeepSeek 系列（默认）+ 多 Provider 注册表** |
| 接口 | 统一 Chat API 抽象层（@novel-wizard/ai-provider） |

### 评价

| 维度 | 评分 | 说明 |
|------|------|------|
| 模型多样性 | 🟢 好 | 支持任意 OpenAI-compatible API |
| 可切换性 | 🟢 好 | Provider 注册表机制 |
| 国内可用性 | 🟢 好 | DeepSeek 国内直连，延迟低 |
| 成本 | 🟢 低 | DeepSeek 价格远低于 GPT-4 |
| 流式支持 | 🟢 好 | SSE 流式输出已实现 |

### 替代方案

| 方案 | 优势 | 劣势 |
|------|------|------|
| **DeepSeek ✅** | 性价比极高，中文优秀，国内可用 | 英文稍弱于 GPT-4，生态工具少 |
| **OpenAI (GPT-4)** | 综合能力最强，生态最大 | 价格高，国内需代理 |
| **Claude (Anthropic)** | 长上下文，写作能力强 | 价格高，国内访问不便 |
| **本地模型 (ollama)** | 数据不出本机，无 API 成本 | 能力受限，需 GPU |

### 结论

**Provider 抽象层是正确决策**。这不是过度设计——AI 领域的变化速度决定了必须可切换。建议持续跟踪：
- `@novel-wizard/ai-provider` 已实现统一的 `postChat` 接口
- 支持请求级 provider/model 覆盖（对调试和测试极其有用）
- Mock 模式分离了 AI 依赖和业务逻辑

## 10. 副作用与风险点

### 🟢 选得好的

| 决策 | 理由 | 不可替代性 |
|------|------|-----------|
| Vue 3 + Composition API | 内容编辑场景精确响应 | 🔄 可切换（但成本高） |
| Vite | 生态最优，体验最好 | 💎 当前无替代 |
| TypeScript + Zod | AI 开发的核心基础设施 | ❌ 不可替代 |
| Naive UI | TypeScript 集成最深入 | 🔄 可切换（Element Plus） |
| AI Provider 抽象 | 多模型切换能力 | 💎 关键设计 |
| Vitest | TS 原生，速度快 | 🔄 可切换（Jest） |
| 模块化 API | 可控的功能粒度 | 💎 关键设计 |

### 🟡 需关注

| 决策 | 风险 | 建议 |
|------|------|------|
| SQLite（sql.js） | 多用户场景不可用 | Repository 抽象保留，生产环境换 PG |
| Express | 性能和类型安全瓶颈 | 关注 Hono，需要时改路由层 |
| npm workspaces | 构建缓存缺失 | 当构建超过 30s 时考虑 Turborepo |
| .mjs / .ts 混用 | 不一致增加维护成本 | 统一为 .ts，build 时编译 |

### 🔴 高优先级改进

| 问题 | 影响 | 建议 |
|------|------|------|
| .mjs 文件无类型检查 | 丢失 AI 开发的核心优势 | 迁移到 .ts |
| 部分 route handler 直接查 DB | 破坏 Repository 抽象 | 所有 DB 操作走 repository |
| Session State 大 JSON 存 SQLite | 查询和序列化性能问题 | 考虑 JSON1 扩展或分表 |

## 11. 技术选型总评

### 按阶段评价

| 阶段 | 评分 | 主要扣分项 |
|------|------|-----------|
| 原型阶段（当前） | 🟢 8.5/10 | .mjs/.ts 混用，部分 JSON 存储策略 |
| 生产阶段（目标） | 🟡 6.5/10 | SQLite 不适合多用户，Express 性能瓶颈 |
| 规模化阶段 | 🔴 4/10 | 需要数据库迁移 + 后端框架替换 |

### 推荐的演进路径

```
Phase 1 (原型)     Phase 2 (生产)         Phase 3 (规模)
────────────────────────────────────────────────────────
SQLite + sql.js  → SQLite (本地) / PG (服务) → 分布式 PG + 缓存
Express           → Express (兼容) / Hono   → Hono / Fastify
npm workspaces    → npm / pnpm             → Turborepo
.mjs / .ts 混用   → 统一 .ts               → 统一 .ts
大 JSON 字段       → JSON1 / 分表           → 结构化存储
观测台 (gui-dev)   → 观测台                 → 观测台 + 监控
```

## 12. 对于新项目的建议

如果从零开始做一个类似 NovelWizard 的 AI 应用，建议的技术栈：

```
前端：        Vue 3 + Vite + Naive UI + TypeScript
后端：        Hono（比 Express 现代且兼容好）
数据库：      SQLite (better-sqlite3) → PostgreSQL
类型：        TypeScript + Zod（必选）
测试：        Vitest + Supertest
Monorepo：    npm workspaces → pnpm workspaces
AI：          DeepSeek（默认）+ Provider 抽象
编排：        声明式路由图 + step gate
可观测：      独立 dev-tools 应用 + trace
```

**核心原则**：类型先行（Zod + TypeScript）、AI 可观测（step gate + trace）、AI 无关（Provider 抽象 + Mock 模式）。
