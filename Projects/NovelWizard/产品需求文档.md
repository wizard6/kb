# Novel Wizard — 产品需求文档

> 版本：Ver.0.1.0 重构线
> 状态：活跃开发中，基础架构已就绪，业务功能逐步推进
> 最后更新：2026-06-24（v0.2 审阅完善）

---

## 1. 产品定位

### 1.1 一句话定义

AI 小说创作系统——「可生长的故事世界操作系统」：从灵感种子出发，通过结构化迭代逐步生长出完整的故事世界，区别于「一键成书」式生成器。

### 1.2 核心设计理念

| 理念 | 说明 |
|------|------|
| **种子 → 世界** | 从零散灵感解析为结构化种子，再迭代生长为完整故事 |
| **版本链** | 每次修改产生新版本，支持回退、分支、继承 |
| **Skill 扩展** | 创作能力通过斜杠命令/Skill 系统可插拔 |
| **AI 辅助而非替代** | 用户掌控创作方向，AI 提供补全和扩展 |
| **可生长的架构** | 数据模型和 UI 都支持从短篇到超长篇的演化 |
| **可观测的 AI** | 每一步 AI 推理都在观测台中可见、可断点、可调试 |
| **基座化设计** | 系统本身是一个通用的 AI Agent 基座，NovelWizard 是它的第一个行业应用实例 |
| **模块化优先** | 所有功能在保证效率的前提下全部模块化——每个模块边界清晰、可替换、可独立演进 |

### 1.3 模块化原则

> 这是贯穿整个系统的架构纪律。不是「尽量模块化」，而是「所有功能必须模块化，除非能证明模块化导致不可接受的效率损失」。

| 层面 | 模块化要求 | 效率权衡 |
|------|-----------|----------|
| 🧩 **功能模块** | 每个业务能力是独立模块（Skill），有明确输入/输出契约 | 模块间调用不走 RPC，同进程内函数调用，零额外开销 |
| 📦 **代码包** | 每个 package 有清晰的公开 API（index.ts），内部实现完全隐藏 | 构建时 tree-shaking 消除未使用代码，无运行时开销 |
| 🔌 **扩展点** | 新增能力=注册新模块，不修改已有代码 | 注册表查表分发，O(1) 开销 |
| 🎨 **UI 组件** | 每个 UI 区域是独立组件，可替换、可复用 | 按需加载（lazy import），不增加首屏体积 |
| 🗄️ **数据访问** | 所有 DB 操作走 Repository 接口，实现可切换 | Repository 是薄封装，零抽象开销 |
| 🤖 **AI 编排** | 每个路由节点是独立模块，可独立开关 | 顺序路由图，命中即返回，无多余遍历 |

### 1.4 双层定位

| 层 | 定位 | 用户 |
|----|------|------|
| 🏗️ **基座层 (Kernel)** | 通用 AI Agent 运行时 + Skill 系统 + 可观测框架 | AI 应用开发者 |
| 🎯 **应用层 (NovelWizard)** | AI 小说创作系统——基于基座层构建的第一个行业应用 | 小说创作者 |

基座层设计为领域无关，替换 domain 模型、注册新 Skill、更换 UI Shell 即可产出全新的 AI 原生应用。

### 1.4 目标用户

- 小说写作者（网文/传统文学）
- 世界观构建爱好者
- AI 辅助创作探索者
- 开发者/调试者（通过 gui-dev 观测台）

## 3. 优先级定义

| 标签 | 含义 |
|------|------|

## 4. 功能需求

#### 4.1.1 灵感输入与解析

| 种子完整性评估 | P1 | completeness skill 提示用户补充缺失信息 |

#### 4.1.2 版本链管理

| 版本与种子关联 | P1 | seed_id 外键关联全局快照 |
| 版本列表查看 | P1 | 按会话分组，显示版本标签 |
| 版本删除 | P1 | 可删除单个版本 |

#### 4.1.3 灵感会话

| 需求 | 优先级 | 说明 |
|------|--------|------|
| 创建会话 | P0 | 灵感工作区的基本容器 |

#### 4.1.4 Skill 操作

Skill 是灵感工坊的核心能力单元，通过斜杠命令或 AI 自动路由触发。

| Skill | 阶段 | 功能 | 触发方式 |
|-------|------|------|----------|
| inspiration-parse | core | 解析原始灵感为结构化种子 | `/parse` + 自动 |
| inspiration-expand | core | 扩展世界观细节（地点/人物/势力） | `/expand` |
| inspiration-completeness | core | 评估种子完整度，提示缺失项 | `/completeness` |
| inspiration-highlights | core | 提取亮点/关键元素 | `/highlights` |
| inspiration-speculate | core | 推测未提及的方向与可能性 | `/speculate` |
| inspiration-rewrite | core | 改写底稿 | `/rewrite` |
| inspiration-chapter-outline | core | 生成章节大纲 | `/outline` |

#### 4.1.5 灵感澄清流程

| 需求 | 优先级 | 说明 |
|------|--------|------|
| AI 对模糊表述提问澄清 | P1 | 当输入信息不足时反向提问 |
| 用户回复后继续解析 | P1 | 澄清对话回合并入解析上下文 |
| 跳过澄清直接推测 | P1 | 用户可选择让 AI 自行推测缺失信息 |

### 4.3 P3 — AI 写作与 Skill 系统

#### 4.3.1 Skill 架构

| 需求 | 优先级 | 说明 |
|------|--------|------|
| Skill 目录 SSOT | P0 | 22 项 Skill 元数据统一注册（catalog.ts） |
| 斜杠命令触发 | P0 | `/skill-name` 快捷调用 |
| 多执行通道 | P1 | skill-run API / dedicated-api / document 动态挂载 三种通道 |
| Mock/LLM 双路径 | P1 | 开发期 mock 模拟，生产环境接真实 LLM，输出带 mock 标记 |
| Skill 结果摘要 | P1 | 执行结果自动生成自然语言总结（skillResultSummary） |
| Handler 注册表 | P1 | skill → handler 的映射表，新 skill 只加 handler 文件 + catalog |

#### 4.3.2 Skill 选择策略（skill-select）

AI 在回合流转中按以下策略链决定是否触发 Skill：

| 策略 | 触发条件 | 优先级 | 说明 |
|------|----------|--------|------|
| 斜杠命令 | 输入以 `/skill-name` 开头 | 高 | 显式触发 |
| 关键词匹配 | 输入匹配 Skill 目录关键词 | 中 | catalogKeywordStrategy |
| LLM 调度 | 模型自主判断用户意图 | 低 | model-router，需开启 flow-model-route |
| chat 回落 | 上述均未命中，走普通对话 | 兜底 | chatFallbackStrategy |

#### 4.3.3 文档挂载（document-load）

运行时可动态将 Skill 文档注入 AI 上下文，使模型理解如何操作。

| 需求 | 优先级 | 说明 |
|------|--------|------|
| Skill 文档声明 | P1 | 每个 Skill 声明自身文档（manifest + capabilities） |
| 动态匹配 | P1 | 根据用户输入匹配并挂载对应的 Skill 文档 |
| 上下文注入 | P1 | 挂载的文档作为 system prompt 注入 |
| 挂载缺失提示 | P1 | 匹配到但缺少上下文时向用户补充提问 |

#### 4.3.4 回合流转（Turn Flow）

AI 单轮对话的路由决策管线，由声明式路由图驱动：

```
order 0:  fixed:delegate       ← 委托给其他 Agent
order 10: fixed:flow-continue  ← 上轮 AI 声明的 flowNext 续接
order 20: fixed:skill-select   ← Skill 选取（可配置开关）
order 30: model:route          ← LLM 意图路由（可配置开关）
order 40: fallback:chat        ← 兜底纯聊天
```

| 需求 | 优先级 | 说明 |
|------|--------|------|
| Agent 委托 | P1 | 将轮次委托给其他 Agent（如委托给规划器） |
| flowNext 续接 | P1 | AI 回复中声明下一步操作类型 |
| Skill 自动选取 | P1 | 基于策略链路由到合适 Skill |
| 循环/多步执行 | P2 | 支持 flowNext 循环、多步自动执行 |
| LLM 意图路由 | P2 | 模型自主判断用户意图并路由 |
| 步骤开关 | P1 | RuntimeStepGate 控制每个步骤是否执行（用于断点调试） |

#### 4.3.5 上下文管理（context-builder）

| 需求 | 优先级 | 说明 |
|------|--------|------|
| 种子上下文注入 | P0 | 世界种子作为对话背景 |
| Skill 文档挂载 | P1 | 按需插入 Skill 说明文档 |
| 知识检索 | P2 | 从标签库/知识库检索相关信息，注入 retrievedBlock |
| 上下文窗口管理 | P2 | 历史对话裁剪与压缩 |
| Skill Resolver 注入 | P1 | setSkillResolver 机制，允许动态注册 Skill 上下文提供者 |
| 分层打包 | P1 | context 按层组织（基础层/Skill 层/知识层），每层可独立开关 |

#### 4.3.6 AI 提供方管理

| 需求 | 优先级 | 说明 |
|------|--------|------|
| 多模型支持 | P0 | 支持 DeepSeek 系列等多种 AI 模型 |
| Provider 注册表 | P0 | 提供方注册机制，API 层统一调用 |
| 请求级覆盖 | P1 | 可在请求中指定 provider/model/apiKey 覆盖默认配置 |
| 环境变量注入 | P1 | 从 .env 读取 API key 等敏感信息 |
| SSE 流式响应 | P1 | 对话支持流式输出 |

#### 4.3.7 Agent 间 Skill 调用

> 核心扩展点：Agent 可以**主动调用** Skill，而不是只能等用户触发。

| 需求 | 优先级 | 说明 |
|------|--------|------|
| Skill 程序化调用接口 | P1 | 提供 `invokeSkill(skillId, params)` API，Agent 可按需调用 |
| 调用上下文传递 | P1 | Agent 可将当前对话上下文、种子、状态传递给 Skill |
| 结果回写 | P1 | Skill 执行结果自动写回 Agent 的对话历史 |
| 多 Agent 共享 Skill | P1 | 同一 Skill 可被不同 Agent 调用，输出因上下文而异 |
| Skill 链式编排 | P2 | Agent A 调用 Skill X，结果传给 Agent B 调用的 Skill Y |
| 调用权限控制 | P2 | 控制哪些 Agent 可以调用哪些 Skill |

对比用户触发 vs Agent 触发：

| 维度 | 用户触发 | Agent 触发 |
|------|----------|------------|
| 入口 | 斜杠命令 / 关键词 / LLM 路由 | `invokeSkill()` 程序化调用 |
| 用途 | 用户主动操作 | Agent 自主决策、链式编排、自动流程 |
| 典型场景 | `/parse` 解析灵感 | 规划器 Agent 调用 `parse` → `expand` → `completeness` 三步链 |

### 4.5 P4 — 作为基座框架（Kernel）

> 系统不仅是 NovelWizard，更是一个可复用的 AI Agent 基座。本节记录基座化需求。

#### 4.5.1 领域层可替换

| 需求 | 优先级 | 说明 |
|------|--------|------|
| 领域类型抽象 | P2 | 核心实体类型定义为泛型/接口，业务层通过继承/实现注入具体领域 |
| 业务无关的编排层 | P1 | 回合流转路由图不依赖小说领域概念，纯以 Agent + Skill 为中心 |
| 数据存储抽象 | P1 | Repository 接口不绑定 NovelWizard 的表结构 |

#### 4.5.2 Skill 系统跨域复用

| 需求 | 优先级 | 说明 |
|------|--------|------|
| 领域无关的 Skill 目录 | P1 | Skill catalog 不写死领域标签，category 可扩展 |
| 应用层 Skill 注册 | P2 | 不同应用注册自己的 Skill，基座只提供执行环境 |
| Skill 包可独立分发 | P3 | Skill 可作为 npm 包单独发布和安装 |

#### 4.5.3 UI Shell 可替换

| 需求 | 优先级 | 说明 |
|------|--------|------|
| Shell 与 Logic 分离 | P2 | 对话壳层 UI（chat-shell-ui）与应用领域 UI 解耦 |
| 主题系统 | P1 | gui-theme 设计 token 化，新应用只需替换 tokens |
| 插件式 Sidebar | P3 | 侧栏路由可由应用层注册 |

#### 4.5.4 扩展路径

从 NovelWizard 到新应用的最简路径：

```
① 替换 domain 包       ← 新领域的数据模型
② 注册新 Skill         ← 新领域的能力单元
③ 更换 UI Shell        ← 新应用的界面
④ 配置 AI Provider     ← 新应用的默认模型
⑤ 调整编排路由图       ← 新应用的 AI 行为

→ 得到一个全新的 AI 原生应用
```

### 4.6 P4 — 硅灵反射（Silicon Reflection）

规划器(Planner) ↔ 执行器(Executor) 之间的结构化方法调用协议。

| 需求 | 优先级 | 说明 |
|------|--------|------|
| Method Call 编码 | P1 | 规划器将意图编码为结构化方法调用（encode.ts） |
| 执行器解析 | P1 | 执行器解析调用并执行对应操作（parsers.ts / execute.ts） |
| IO Profile | P1 | 每个方法定义输入/输出 schema（ioProfiles.ts） |
| 方法注册表 | P1 | registry 管理可调用的方法 |
| 反射接口 | P2 | 规划器可查询执行器提供哪些方法 |

### 4.7 P4 — 零记忆协议（Zero Memory）

统一数据获取协议，屏蔽知识库/书架/档案/文档等不同数据源的差异。


### 9.2 开发目标（两线并行）

#### 线 A — 基础架构收尾（NovelWizard 自身）

| 编号 | 任务 | 优先级 |
|------|------|--------|
| A1 | API 契约收尾（兼容层/错误体统一/路由清单） | 高 |
| A2 | LLM 编排骨架（orchestrator/JobIntent/执行器抽象/规划器/调度器） | 高 |
| A3 | Skill 运行时骨架（Handler 注册表/按 skill 拆文件/persona 独立 API/LLM 分发层） | 高 |
| A4 | 域路由与前端目录约定（stubs 拆分/features 目录/store 占位） | 中 |
| A5 | 质量与文档基座（verify 扩展/对外文档/里程碑评审） | 中 |

#### 线 B — 基座化与可扩展性（面向复用）

| 编号 | 任务 | 优先级 |
|------|------|--------|
| B1 | **Agent 间 Skill 调用接口** — `invokeSkill(skillId, params)` 程序化 API | 高 |
| B2 | **Skill 链式编排** — Agent A 调用 Skill X → 结果传给 Agent B → Skill Y | 中 |
| B3 | **领域层剥离** — 将 NovelWizard 特有类型与通用基座类型分离 | 中 |
| B4 | **UI Shell 解耦** — chat-shell-ui 与领域 UI 分离，支持换肤和换壳 | 低 |
| B5 | **示例应用 / 模板** — 提供一个最小可运行的空白基座模板 | 中 |
| B6 | **Skill 包分发机制** — Skill 独立 npm 包，可安装/卸载 | 低 |

### 9.3 实施建议顺序

```text
第一阶段（基础就绪）：
  A1（契约）→ A3（Skill 骨架）→ B1（Agent 调 Skill）
  
第二阶段（编排与复用）：
  A2（编排骨架）→ B2（Skill 链式编排）→ B3（领域剥离）

第三阶段（生态与质量）：
  A4（域占位）→ B4（UI 解耦）+ B5（示例模板）→ A5（质量与文档）

第四阶段（成熟）：
  B6（Skill 分发）
```

### 9.4 暂缓项

> 业务功能（P3 灵感工坊补全 / P4 书架大纲 / P5 扩展域）已登记但明确暂缓实现，
> 直到基础架构收尾（A1-A5）以及基座能力（B1-B3）初步完成。

## 10. 关键术语表
